# C-regime 对照 TB12 三条奖励裂缝(5080 回执)

2026-08-25。回 `reports/tb12/RL_PAIR_VERDICT.md` 与 `RL_FIX_PROPOSAL.md`。
G1 战役正在跑同一个奖励家族,所以逐条查了裂缝是否在 C-regime 成立。**结论:三条都不成立,但第②条只是没被触发,不是不存在。**

## 逐条比对

| 裂缝 | TB12 | C-regime | 判定 |
|---|---|---|---|
| ① 归一化棘轮(runningMax 跨 episode 只涨不跌) | 成立 | `carbon_normalization_mode: FIXED`,`fixed_max=5e-05 > 0` | **不成立**。Java 侧 `MultiDatacenterSimulationCore.java:1907` 确认 FIXED 分支走固定分母,完全不碰 `runningMaxCarbon` |
| ② 3.0 封顶使爆发式排放免罚 | 成立 | 封顶存在(`CARBON_RATIO_MAX = 3.0`,两种模式都套),但**实测从未接近** | **未触发**。五个臂逐 episode 的 `global_carbon_penalty_norm_mean`:min 1.213 / 中位 1.618 / max 1.803,离 3.0 有 40% 余量 |
| ③ γ 折扣使推碳套利 | γ=0.99 → 150 步打 0.22 折 | **γ=0.999** → 150 步打 0.86 折 | **弱得多**。且 C-regime 是 8000 作业 / 7200 步连续到达,碳反馈的时间尺度远短于 TB12 的 5 作业 / 24h |

## 一处需要你们确认的出入

仓库里 `experiment_tb12_rl_fc` 写的是:

```
carbon_normalization_mode = FIXED
carbon_normalization_fixed_max = 2e-05
gamma = 0.999
```

而判决里的机制描述是 runningMax 棘轮和 γ=0.99。两者对不上。可能是训练时用的不是这个 block(本地覆盖?),也可能是判决行文取整。**这个出入会影响修复提案 R1 的必要性** —— 如果 FIXED 本来就生效,R1 要修的就不是归一化模式,而是别的东西。请核一下实际训练用的 resolved config。

## 采纳你们的 R3

"奖励改善必须与物理 kg 同向,否则第一时间止损" —— 这条我们接受,并且承认它和 `crd_dr ≡ 0` 那组止损是同一类。区别在于:`crd_dr` 查的是**通道有没有信号**,R3 查的是**信号指向的是不是真东西**。后者更根本,因为通道可以健康地指向错的量。

本轮 G1 已经跑了一半,不改在跑的东西;但这条应当写进下一轮的开跑前清单,和 `crd_dr`/`rho_routing`/`c_t` 三条并列。

## 对论文的影响

TB12 作为第二考场这一轮走不通,已确认。缺陷清单里 **C1(单一考场)和 C3(污染是合成的)因此没有实验解,只能进 Limitations**。机时账不受影响 —— TB12 昨天已从 229h 的计划里摘出,标为"候选不是资产"。
